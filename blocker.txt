BLOCKER-002: Production & Staging Cryptographic Secret Configuration
================================================================================
- ID: BLOCKER-002
- Title: Configure Production JWT and HMAC Cryptographic Secrets
- Priority: CRITICAL (P0)
- Module: Authentication & Security (FR-1, SR-01)
- Spec Requirement / Gate: FixHub-Product-Spec-v1.3.md (FR-1), Quality Standard Cat 12
- Status: READY_FOR_OWNER
- Problem: The repository is public. A default JWT secret string was historically
  committed in PR #21 and is publicly visible in git history.
- Verified Cause: `api/services/auth-service.ts` originally contained a fallback secret.
- Current State: Code-level quarantine is active. The backend refuses to start and halts
  immediately in non-test environments if `JWT_SECRET` is unset, < 32 chars, or equals
  the leaked default string.
- Impact: Production or staging deployments will crash intentionally on startup until
  the owner provisions unique, secure secrets.
- What Was Tried: Investigation documented in `docs/investigations/fr-1-jwt-secret.md`.
  Startup enforcement guard implemented and tested.
- Work Completed: Hardcoded fallback removed; startup validation added; negative tests
  passing in `api/test/security-quarantine-fr1.test.ts`.
- Why Autonomous Resolution Is Unsafe: AI agents must never generate production secrets
  or store real cryptographic keys in code repositories.
- Exact Owner Action: Generate a cryptographically random 64-character secret and inject
  it into the server environment configuration (never commit to git).
- Step-by-Step Instructions:
  1. Open a secure terminal on your local machine.
  2. Run the command:
     node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
  3. Copy the resulting 64-character hex string.
  4. In your production hosting environment (or local `.env` for production runs), set:
     JWT_SECRET=<your-generated-64-char-hex-string>
     AUTH_HMAC_SECRET=<your-generated-64-char-hex-string>
  5. Ensure these environment variables are never committed to version control.
  6. Session Invalidation Procedure: Purge any pre-existing session records from the database
     via `TRUNCATE auth_sessions;` so no legacy sessions survive rotation.
  7. Activity Audit: Review `audit_logs` table and access logs to confirm no unrecognized
     privileged actions or unauthorized booking states occurred prior to rotation.
- Environment Variable Names: `JWT_SECRET`, `AUTH_HMAC_SECRET`
- Dependencies: Owner terminal and hosting environment secrets manager.
- Expected Result: Backend starts in production mode without security violation errors.
- Verification: Start server with production environment variables; verify 200 OK on `/health/live`.
- Tests to Rerun: `npm run test:smoke`
- Evidence: `docs/investigations/fr-1-jwt-secret.md`.
