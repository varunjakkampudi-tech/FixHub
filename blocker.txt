================================================================================

- Priority: P0 (CRITICAL)
- Module: Authentication and security (FR-1, SR-01)
- Requirement or gate: FR-1; Engineering Standards section 2; Quality Standard section 22
- Status: READY_FOR_OWNER

- Problem: A default signing string was committed in commit #21 (merged through PR #21)
  and is visible in the public repository history.

- Verified cause (verified fact):

    to reject that value at startup in non-test mode.
  - The earlier fallback was introduced in commit a534af0 and merged through commit
    dd1bc789ae372c80281a7e4f3d11768a48ccaaab (see docs/investigations/fr-1-jwt-secret.md).

- Current state (verified fact):
  - getAuthJwtSecret() in api/services/auth-service.ts refuses to run outside test mode
    unless JWT_SECRET or AUTH_HMAC_SECRET is set, has at least 32 characters, and is not the
    leaked value.
  - Regression tests: api/test/security-quarantine-fr1.test.ts (12 tests on the task branch;
    10 on main).

- Corrections in this checkpoint:
  - Earlier step 6 said to run TRUNCATE auth_sessions. No table with that name exists.
    The session table in api/migrations/001_identity.sql is identity_session.
  - Earlier step 7 referred to an audit_logs table. No table with that name exists in
    api/migrations. Audit storage is not implemented yet.
  - The investigation record says FixHub24 "has never had a public staging or production
    server deployed". That is a statement from repository search only. The agent cannot
    check hosting accounts, provider consoles or deployment logs. The owner must confirm it.

- Impact: If any environment (including a demo or preview host) ever ran with the default
  secret, tokens signed with it must be treated as compromised.

- What was tried: Repository history search, CI workflow review, .env review and
  documentation search (see docs/investigations/fr-1-jwt-secret.md).

- Why autonomous resolution is unsafe: Secret generation and rotation happen only in the
  owner's hosting environment. The agent must not hold or create production keys.

- Exact owner action:
  1. Confirm, for every hosting account, preview host and demo host you have used, whether
     the default string was ever set in its environment. Record the answer in
     docs/investigations/fr-1-jwt-secret.md through a reviewed change.
  2. If it was set, or you cannot rule it out, rotate the secret (steps below).

- Step-by-step instructions:
  1. Generate a 64-character hex value in a trusted local terminal:
       node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
  2. In each hosting environment, set JWT_SECRET to that value. Set AUTH_HMAC_SECRET only if
     your deployment still uses it. Do not commit either value.
  3. Invalidate existing sessions. The current database session table is identity_session
     (api/migrations/001_identity.sql). Remove its rows only after backing up the database
     and reviewing them with the database owner.
  4. Review authentication activity for the affected period. No audit table exists yet, so
     use your hosting provider's logs.
  5. Record the rotation date and the reviewer in docs/investigations/fr-1-jwt-secret.md.

- Environment variable names: JWT_SECRET, AUTH_HMAC_SECRET (names only).
- Dependencies: BLOCKER-010 and BLOCKER-011 (two token-issuing paths are still mounted).
- Expected result: Startup in non-test mode fails without a valid, non-leaked secret.
- Verification: Start the API with NODE_ENV unset and no secret: it must exit with the
  FATAL_SECURITY_ERROR message.
- Tests to rerun: npm run test:security
- Evidence: api/services/auth-service.ts; api/test/security-quarantine-fr1.test.ts;
  docs/investigations/fr-1-jwt-secret.md
