# Local API foundation

**Status: LOCAL DEMONSTRATION ONLY — NOT A PRODUCTION API.** The service is a first implementation increment, not an approved Phase 03 exit, production deployment, security certification, or live marketplace backend.

## Run and inspect

From the repository root, copy `.env.example` to an ignored local `.env` if configuration changes are needed, then run `npm run dev`. Vite serves the UI at `http://localhost:5173`; a separate Express API listens on `127.0.0.1:4000`. Vite proxies `/api`, `/health`, and `/docs` only in development. Swagger UI is at `/docs/`; the OpenAPI document is at `/openapi.json`.

Current routes include process liveness/readiness, a read-only fictional baseline price example, optional PostgreSQL-backed email-code customer sign-in, customer-owned addresses and COD booking requests, and merchant offer responses for pre-provisioned verified merchant identities. After assignment, the owning customer can explicitly approve the exact current price terms; the verified merchant cannot start accepted work until the saved quote hash still matches that approval. Parts shown as separate/unknown are excluded from quote approval and require separate approval before that work begins. The owning customer may confirm completion and submit one private rating. For a completed booking with currently matching quote consent, the customer can print/save a service summary; it excludes the full street address and explicitly is not a tax invoice or payment receipt. Actual bill/receipt issuance, payment status, tax, and issuer identity remain unimplemented pending owner and qualified legal/tax decisions. `GET /api/v1/demo/prices/{category}` uses illustrative rates, labels the response `demoOnly`, and does not create a quote, order, or payment instruction. Persisted bookings use configured verified-merchant pricing; they do not collect online payment. Unknown categories and malformed/oversized JSON receive bounded error envelopes. These transactional outbox events are not delivered notifications: no WhatsApp outbox worker, customer/merchant consent flow, merchant self-onboarding, public rating display, or rating moderation is implemented. No photo upload endpoint exists.

Production readiness intentionally returns `503` until an explicit production-readiness approval is recorded; configured infrastructure alone does not clear security, privacy, legal, operational or release gates. Browser-local demo personas are not authentication and must never authorize server operations.

## Controls in this increment

- Helmet applies secure HTTP response headers; Express' `X-Powered-By` banner is disabled.
- CORS allows only exact configured web origins and allows credentials only to those origins for cookie-based auth. CORS is a browser policy, not authentication or authorization.
- `express-rate-limit` limits API requests with standard headers and no legacy headers. Its default in-memory store is per-process and is **not** a multi-instance or distributed abuse-control solution. The server does not trust forwarded IP headers; a future reverse proxy requires a narrowly configured trusted-proxy boundary before IP-based limits can be relied on.
- Pino HTTP logging records a generated request ID, method, route template and response status. The API returns that ID as `x-request-id` and exposes the header to exact allowed browser origins so a client can include it in a support report. Query strings, request bodies, headers, contact fields and exception messages are not logged by these serializers. Logs remain local stdout; there is no retention, alerting, or admin log viewer.
- Zod validates route parameters and environment origins. JSON bodies are capped at 32 KiB and malformed/oversized bodies have generic error responses.
- OpenAPI 3.1 and Swagger UI document only the routes that exist today.

These controls have focused local tests; they are not a completed threat assessment and do not prove application security.

## Location and directions boundary

The customer address editor requests browser geolocation only after the user selects its location button; the browser permission prompt remains user-controlled. For a persisted job assigned to the signed-in verified merchant, the jobs page offers an explicit Google Maps directions link to the saved job coordinates. Opening that link sends the destination to Google Maps. It uses Google's keyless Maps URL handoff, not the paid Maps Platform API; it does not geocode addresses, search places, share location in the background, or provide FixHub-side live tracking. The demo screen's SAMPLE data must not be used as a real dispatch destination.

## First persisted identity increment — 2026-10-16

The current feature branch adds PostgreSQL pool configuration with bounded connection/query timeouts and production TLS certificate verification, checksum-verified ordered SQL migrations, email-code authentication, a Resend email adapter, and a Twilio WhatsApp approved-template sender adapter. Migrations create identity subjects, explicitly granted roles, sessions, catalog, merchant/service configuration, customer addresses, bookings with cash-on-completion-only payment method, merchant-offer records, reviews, idempotency records, privacy-request records and a transactional outbox. Migration-history correction: `002_marketplace.sql` at original checkpoint `f5c4b93` has normalized SHA-256 `d60f1e18469f43ec987d6bf268af468439c49fba18edd4016f53e3f3d12fc674`; merged PR #17 changed those bytes in place (current-main `9ffabee` checksum `f474bbedece28a7503b92fc24d82e84114c3ed585ed58aa2adfa9fcdc41f4e35`). This patch restores the original bytes, and `003_nullable_parts_estimate.sql` carries the nullable-field change forward. Migration 004 stores customer quote consent against a SHA-256 digest of the exact itemized prices, currency and COD method; the verified merchant start endpoint rechecks that digest. It does not authorize or verify payment. The migration runner accepts only the original and this exact accidentally published 002 checksum while recovering existing records; unrelated checksum drift still fails closed. Tests seed both hashes as historical database states, rather than deriving the recorded 002 value from source. No PostgreSQL database migration or deployment was run, so compatibility is verified by checksum logic and regression tests, not by a live database upgrade. Booking requests use an authenticated owner-scoped address, a payload-bound idempotency key, verified/accepting merchant eligibility and the merchant's configured travel radius; intended-offer and outbox records are committed together. Offers expire after 15 minutes. A pre-provisioned, verified merchant account can list its own pending offers and atomically accept one or decline it; acceptance claims the booking only if it is still unassigned, snapshots that merchant's offer price, and cancels competing offers. The saved booking status is `offered` until a merchant accepts. A verified assigned merchant can move an accepted booking to `in_progress` only after the customer approves the current quote; only the owning customer can confirm completion from that state and then create one private rating. Completion, quote approval and rating actions use idempotency keys. The customer must affirm completion in the UI; this state does not verify payment or issue an invoice. The merchant portal remains pull-to-refresh only: no outbox worker, WhatsApp dispatch, provider delivery receipt, or automatic customer refresh is implemented. Outbox payloads contain opaque identifiers, not the customer's address or phone. Customer account deletion can be requested; the API disables access and revokes sessions but does not claim immediate erasure or resolve legal retention/holds. The OTP is six digits, stored only as a keyed HMAC, expires after ten minutes, has a five-attempt cap, is single-use, and is throttled per normalized email in persistent storage. Sessions are random, persisted by HMAC, HttpOnly/SameSite cookies with a separate CSRF token; newly created identities receive only the `customer` role. Existing roles must be explicitly provisioned; the email flow does not let users self-assign merchant, technician, support, or admin access.

The local regression suite exercises auth with a fake PostgreSQL client, a mocked email sender, and mocked provider transports; it does not prove live Resend deliverability, Twilio account eligibility, WhatsApp template approval or consent, database behavior, migration compatibility against production data, multi-instance rate limiting, identity-provider compliance, security certification, or production readiness. The Resend integration is disabled without both `RESEND_API_KEY` and `RESEND_FROM_EMAIL`; Twilio requires complete credentials, an approved WhatsApp sender, and a Content SID. No credentials or provider account were created and no outbound message was sent. Set provider secrets only in a private local environment. Do not put secrets in `.env.example` or tracked files. Production readiness remains deliberately blocked by code and cannot be enabled by setting environment variables.

## Explicitly not implemented

- Account recovery, merchant/technician onboarding and role review, complete tenant authorization, outbox worker and retries, deletion-request adjudication/erasure, support/admin operations, public rating display/moderation, or real-time cross-device updates.
- Twilio/WhatsApp outbox dispatch, recipient phone verification and consent management, WhatsApp callbacks, and Google Maps Platform requests. The provider adapter is not called by the application. Actual provider account setup, sender eligibility, approved templates, recipient opt-in, credentials, quotas, billing and legal terms remain owner-controlled prerequisites.
- Online payments are deferred. The demo's cash-on-completion label is not a live collection workflow.
- Production logging/monitoring, distributed rate-limit storage, backup/restore, deployment, service-level objectives, incident response, or production support.

Booking/merchant mutations and external message delivery must not be treated as live until the remaining APIs, ownership/eligibility checks, reliable outbox worker, consent/preferences, provider policy/cost and operational prerequisites are implemented and independently assessed.
