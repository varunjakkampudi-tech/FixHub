# Verification, fraud and customer safety

Status: proposed control plan, effectiveness NOT ASSESSED. [Lawful verification](../legal/merchant-verification.md), [trust boundaries](../../../architecture/security-trust-boundaries.md).

| Risk | Proposed prevention / response | Unproved dependency |
|---|---|---|
| False business/technician identity | Consent-led least-data checks, scope/expiry and reviewer reason | Lawful documents, qualified verifier, private storage |
| Dangerous task or skill mismatch | Explicit exclusions, category credentials and refusal/escalation | Trade/legal/field assessment |
| Fake completion/fee dispute | Versioned booking evidence, party confirmation and human appeal | Completion policy, collection audit |
| Duplicate leads/ratings | Backend deduplication, completed-job-linked reviews, abuse monitoring | Runtime/UGC tests and staffed moderation |
| Account takeover/tenant leakage | MFA privileged access, narrow staff scope, revocation and deny tests | Future security implementation |
| No-show/unsafe access | Honest ETA, check-in/escalation and safe reassignment | Real provider availability and staffed backup |
| Private photo/ID leak | Private scope, minimal data, scan, retention and incident procedure | Storage/vendor/test proof |
| Staff conflict/abuse | Assign-case scope, audit/reason and independent escalation | Staffing separation and governance |

Verification is a limited dated check, not a universal safety guarantee or insurance. No raw Aadhaar/biometrics/private criminal checks authorized. Fraud controls must preserve legitimate appeals; never hide original allegation/context without lawful reason.

Before launch: trained staff, qualified trade competence process, insurer/legal scope if required, defined incident coverage, safe task refusal, customer/merchant terms and tested controls. Founder availability alone cannot satisfy independent/high-risk roles. No security percentage fabricated.
