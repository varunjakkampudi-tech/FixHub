2. `/communications/preferences`: explicitly opt into transactional SMS and WhatsApp demo channels and save. Do the same for SAMPLE Merchant A/B in two same-origin tabs. In-app notifications remain independent, marketing stays OFF. Unsubscribe then resubscribe creates audit entries; queued messages are suppressed after opt-out.
3. Existing booking wizard: choose Tanuku, electrician, SAMPLE problem, confirmed saved sample address, future weekday morning (e.g. 2026-10-22 after fixture reset), review inspection ₹149 + labor ₹450 + parts ₹200 + fee ₹0 − discount ₹0 = ₹799 before unconfigured applicable taxes. Submit. Both eligible merchants get in-app unread notifications and queued external DEMO rows. Eluru and Bhimavaram use the existing city-specific eligibility; no whole-city/live-market claim.
4. Merchant A: `/communications/conversation`, choose WhatsApp channel/new DEMO ID; review via FixHub24 link. **Accept via DEMO reply** validates the recipient/offer/expiry demo token then calls the existing canonical acceptance command. Merchant B sees closed. A forged/stale reply fails. Delivery `accepted`, `delivered`, `read` never accepts a booking. Demo tokens are openly inspectable, not signed production action tokens. Merchant A assigns Technician A in the existing job page.
5. Technician travel → arrived → inspection, submit a revised quote (e.g. ₹300 parts gives ₹899). Customer explicitly approves this fresh version; start and complete. Use `/demo` reset to clear the whole shared fixture state. SAMPLE Customer A/B, Merchant A/B/C and 4–8, Technician A/B/C and 4–8, Operations and Super Admin are fictional selector identities, not real passwords/accounts/phone numbers. Fictional `+91 DEMO C1`-style tokens intentionally are NOT routable E.164 numbers. Optional unsaved phone-format preview supports E.164 normalization/masking but never calls Verify.

## Message and policy boundaries
- Canonical booking notifications generate two channel rows per recipient. Defaults suppress both without explicit consent. Rows use `DEMO-message-…` IDs; provider receipts are always null and never imitate Twilio SIDs.
- Typed catalogue includes OTP, request, reminders/expiry, acceptance/decline/closed, assignment, travel/arrival/reschedule/inspection, quotes/approval/rejection, work/completion/cancellation/dispute/support and outages. Automatic generation covers existing committed booking events; reminder/outage scheduling and OTP delivery-row persistence are not complete.
- Language-specific DEMO templates exist for catalogue events; Hindi remains future-gated. Displayed conversations use EN/TE and sanitized summaries, not customer house addresses. Editing approved template text affects template policy; the conversation summary remains centralized, not a full rendering engine for arbitrary template parameters/buttons.
- Consent, recipient scope, template/language/purpose or 24-hour session govern simulated WhatsApp delivery. Session opening is explicitly manual demonstration, not proof of an actual inbound customer message. Every simulated callback modifies delivery only. Merchant acceptance separately rechecks current offer/capacity/status through the existing state machine.
- Same-browser storage/BroadcastChannel notifications and supported Web Locks apply. No cross-device sync, real push/FCM/APNs, SMS/WhatsApp, database privacy enforcement or genuine RBAC. Browser local state is inspectable: never enter actual sensitive addresses, real phone records or credentials.
- Demo rates are unset (zero means unknown, not free). GSM-7 extension characters count twice; Unicode Telugu/Hindi uses 70/67 UTF-16 unit segmentation and GSM-7 160/153 units. Encoding and provider transformations must be confirmed on the actual route. Explicit USD hypotheses and optional FX/tax produce planning costs only; service quotes/earnings never receive messaging charges.
- Daily recipient and overall rolling-month caps are demo counts, not durable provider spend enforcement. Retry is manual, bounded; dead letters are local identifiers, not a durable worker or automated exponential-backoff queue. Aggregate city/message counts exist; invoice-level per-message cost attribution, monthly spend alerts and budget scheduler are future work.

## Provider setup — owner actions only, not enabled
**Real integration: BLOCKED — ACCOUNT / KEY / CONSENT / PRICING / BACKEND AUTHORIZATION.** The existing project has no separately authorized durable backend. The typed provider interface is a deliberately disabled boundary, not a live server adapter or secure webhook implementation. It cannot send even after someone merely adds a connector.

1. Explicitly authorize staging architecture, durable backend and a capped test budget. Approve only consented test recipients and supported countries. Connecting alone is not permission to send.
2. Establish a Twilio account/billing, appropriate Verify Service, sender/routing eligibility, SMS Pumping Protection and country-specific SMS Geo Permissions. Confirm India availability, sender route, Principal Entity/Header/Template/DLT requirements and URL whitelisting with Twilio/account route; do not infer domestic support from generic E.164 validation.
3. Use the supported Twilio connector after explicit authorization; private API credentials remain server-side in secure connector/Secrets settings. No private values in browser/source/logs. Primary Auth Token or a supported official validation arrangement is needed for real Twilio-signature validation; provider gateway sending credentials alone are not assumed sufficient.
4. One FixHub24-owned WhatsApp sender: either Twilio Sandbox for explicitly approved testing or registered official sender/WABA with Meta review/approved language-specific Content SIDs. Sandbox recipients must join the account's sandbox using its official join instructions; do not invent a sender/join code. Sandbox is a test sender, not proof of an approved production FixHub24 number. Confirm 24-hour reply windows and template/button features; web review link is the safe fallback. Do not configure a duplicate Meta-direct sender.
5. Read fresh account-specific prices/India routes before any tests. Public Twilio pages inspected on **2026-10-15 UTC** list **Verify USD $0.05 per successful verification plus channel fees**, and **WhatsApp USD $0.005 per inbound/outbound message plus applicable Meta template fees**. These are planning inputs, not contractual India quotes; current account terms, region, taxes/FX, sender rentals and destination/template costs remain unverified. UI does not populate them as guaranteed prices.
6. Implement/test authenticated, validated server-only Verify start/check with nonenumerating errors, durable monotonic number/user/IP quotas, cooldown/CAPTCHA risk gates and masked logs. Only authoritative provider `approved` may establish possession; server session authorization and merchant approval/admin MFA remain separate. No plaintext OTP persistence/logging.
7. Implement transactional database outbox after committed booking events and durable inbound/status inboxes. HTTPS callbacks must use official Twilio SDK `X-Twilio-Signature` validation with the exact externally configured full URL and raw form/JSON rules; never trust arbitrary forwarded-host headers. Deduplicate delivery/event identities, preserve provider timestamps, monotonic sent/delivered/read outcomes and failed reasons, retry/backoff/dead-letter processing, retention and recovery. Verify signed, expiring action tokens and recipient identity before server-atomic acceptance. Delivery callbacks cannot assign/accept/pay.
8. Deploy receiver only after explicit owner deployment consent, then separately approve limited sandbox sends. Test on physical consenting recipients; record authoritative Verify and real provider receipt/delivery callbacks. Twilio test credentials/magic numbers simulate APIs but don't deliver messages or prove callback/handset success. Stop on billing/credential/regulatory blocks; never auto-activate production.
